## Prerequisites

Before running any CLI commands, verify the tools are present:

```sh
jinks --version   # Jinks CLI
xst --version     # eXist-db CLI
```

If either is missing, install both with:

```sh
npm install -g @teipublisher/jinks-cli @existdb/xst
```

Devcontainer and Docker setups may already include them — check before installing.
Also confirm that eXist-db is running and the Jinks app is installed on it.

## How to make changes

**Always check first whether a change can be made in `config.json`** — that is the
master input and the preferred place to change behaviour. Consult the JSON schema
before editing so you use valid keys and values: fetch it over HTTP from
`<jinks-server>/schema/jinks.json` (default
`http://localhost:8080/exist/apps/jinks/schema/jinks.json`).

All Jinks operations go through the **`jinks`** CLI (verify with `jinks --version`),
which talks to the Jinks app in eXist-db. The core loop after editing `config.json` is:

```sh
jinks update -c config.json --sync
```

**Always use `--sync` with `jinks update`** so generated files on the server are pulled
back into this directory and the local repo stays authoritative. Tell the user which
files changed. See the **update-app-on-server** skill for the other flags, for pushing
local custom files to the server, and for handling conflicts.

Jinks expands `config.json` against the profiles this app
was composed from. To see the effective expanded config, use

```sh
jinks config -x <abbrev>
```

**Configs are merged as follows**:

* properties with an **atomic value** will overwrite earlier properties with the same key
* **objects** will be processed recursively by merging the properties of each incoming into the outgoing object
    + to instead replace an object, add a property `$replace` with value `true` to it
    + to replace certain properties of an object, `$replace` can be an array listing the keys to be replaced
* **arrays** are merged by appending the values of each incoming array with duplicates removed.

## Before you edit any file

Ask these questions **before** changing a path — especially when debugging
`tmpl:error-dynamic` or a failed `jinks update`:

1. Is the path listed in `.jinks.json` with a content hash? → **upstream-owned; do not edit**
2. Did `jinks update` report a **conflict** on this path? → **upstream-owned; undo the edit**
3. Does the file come from a profile in the list above (e.g. `templates/register-blocks.html`
   from `registers`, `templates/browse.html` from `base10`)? → **do not edit**
4. Is it on the allow-list below (`collection.xconf`, `modules/query*.xql`, …)? → **safe**
5. Did **you** create it for this project (`templates/pages/mypage.html`,
   `modules/templates/mymodule.xqm`, `resources/css/my-custom.css`)? → **safe**

When in doubt, treat the file as upstream-owned and add a **new** file instead.

## Rules

**Do not modify files provided by Jinks.** Add customizations to separate files and
register them through the extension points in `config.json` (or in an HTML template's
frontmatter if they are required for a specific HTML page only):

- **Open API endpoints** — custom `.json` spec + XQuery implementation in `modules`; register under `api`
- **CSS** — add files to the `styles` array
- **JavaScript** — add files to `script.custom`
- **Custom templating functions** — register under `templating.modules`
- **HTML templates and named blocks** — see the **customize-templates** skill

Conflicts tell you who owns a file. Anything that came from one of the profiles above has
an upstream version, so `jinks update` reports a conflict once you have changed it —
answering **No** keeps your version, but from then on you are maintaining a fork that
fights every upstream change. A file *you* added for this project has no upstream version,
never conflicts, and is yours to edit freely. That is the point of the rule above: put
customizations in your own files, registered through the extension points, and
regeneration stays quiet.

**`skip` is a last resort, not a debug shortcut.** Only add a regex to `skip` or
`skipSource` in `config.json` when you have **deliberately** decided to own a generated
file for the lifetime of the project (user acknowledged, reason documented, no extension
point exists). **Never add `skip` while fixing an initial error** — it hides the mistake
and blocks future profile updates. See the **update-app-on-server** skill.

When a template error appears, do **not** edit upstream profile files or gut their
content. Read the **customize-templates** skill for extension points, block append vs
overwrite, and debugging steps.

Files you *may* edit directly:

- `collection.xconf`
- `index.xql`
- `modules/navigation*.xql`
- `modules/query*.xql`
- `modules/facets-config.xql`

## Golden rules

1. **Never edit upstream-generated files to fix bugs.** If a page breaks, the cause is
   almost never "the profile template is wrong." Diagnose first; customize via extension
   points or your own files. Adding `skip` to silence Jinks is a last resort, not a debug
   step — see **Before you edit any file**, **customize-templates**, and
   **update-app-on-server**.
2. **`config.json` changed → always regenerate with sync** (`jinks update -c config.json --sync`) before treating the server as up to date.
3. **Always `--sync` with `jinks update`** — without it, server-side changes never reach this repo.
4. `context.json` and `.jinks.json` are Jinks-owned — do not hand-edit.
5. **After editing a `.odd` file**: it must be uploaded and recompiled, and sync will not do it for you — follow the **manage-odds** skill.
6. **TEI → HTML transformations belong in ODD.** ODD is the standardized way to define how TEI is rendered as HTML. Hand-coded XQuery that reimplements the same rendering is discouraged; use it only in the rare cases where going through ODD would be overkill.
7. **HTML files must be well-formed XML** or eXist-db will refuse them.
8. **Do not embed** JavaScript or CSS in HTML — use separate files.
